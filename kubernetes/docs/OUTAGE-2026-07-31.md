# The 2026-07-31 outage — four latent faults, one reboot

**Symptom:** `troophunter.com` and `helloabdul.com` returned HTTP 530, the whole public
stack was down, and it appeared to start with a hub reboot.

**It did not start with the reboot.** Three of the four faults had existed for weeks. The
reboot only *revealed* them, because every one was invisible while the affected process
kept running. That is the single most important thing on this page: **these systems were
broken and serving traffic at the same time.**

This is written down because each cause took real time to find and none is guessable.

---

## 1 · connect-ops — a 2.8 GB disk, 100 % full

```
/usr 1.7 GB + /boot 111 MB   = 1.8 GB before anything of ours exists
/var/lib 563 MB · /var/cache 252 MB (apt) · /var/log 156 MB (journald, uncapped)
disk 2.8 GB total → 0 bytes free
```

**Nothing ran away. The VM was never big enough.** A stock Ubuntu install plus normal logs
and apt cache does not fit in 2.8 GB. It was always going to fill; only the date was open.

The chain: **disk full → `systemd-resolved` cannot start → it never writes
`/run/systemd/resolve/stub-resolv.conf` → `/etc/resolv.conf` (a symlink to it) dangles →
no DNS at all → `cloudflared` cannot resolve `region1.v2.argotunnel.com` → exits.**

With `Restart=on-failure` and a ~100 ms default backoff it restarted **6,066 times**, each
attempt writing log lines into the disk whose fullness caused the failure. A self-feeding
loop.

**Why it looked random:** `/run` is a tmpfs, wiped at every boot. While the machine stayed
up, `stub-resolv.conf` already existed and cloudflared already held its connections, so a
full disk had no visible effect. Only a restart exposed it — which is exactly why it
correlated with *time since build* and nothing anyone did.

**Fixed by breaking the chain, not the symptom:**
- `/etc/resolv.conf` is now a **real file** with static nameservers (`192.168.1.1`,
  `1.1.1.1`), `chattr +i`. A full disk can no longer take DNS down, whatever else fails.
- `systemd-resolved` disabled — nothing left to fight over the file.
- journald capped (`SystemMaxUse=100M`), apt told not to keep packages.
- `RestartSec=30`, which turns 6,066 attempts into roughly 200 and stops the loop feeding
  itself.

**Still to do:** the VM needs resizing (2.8 GB → 8 GB) and rebuilding declaratively.
⚠️ The tunnel token is still **plaintext in the systemd unit**, readable by anyone who can
run `systemctl cat`. It belongs in a `0600` file from ansible-vault.

## 2 · k8s — containerd auto-upgraded 1.7 → 2.2 and the config stopped being understood

```
/var/log/dpkg.log.1:
2026-06-27  upgrade containerd:amd64  1.7.27-0ubuntu1~22.04.1 → 2.2.1-0ubuntu1~22.04.2
```

An unattended upgrade on **27 June**. The running containerd carried on serving CRI from
memory, so nothing broke for five weeks. On the reboot the new binary read the old config:

```
on disk        version = 2   plugin key  io.containerd.grpc.v1.cri
containerd 2.x version = 3   plugin key  io.containerd.cri.v1.runtime
```

CRI was never registered, so kubelet failed with
`unknown service runtime.v1.RuntimeService` — **3,602 times**.

**Fixed** by regenerating the config in the schema this version understands
(`containerd config default`) and re-setting `SystemdCgroup = true`, which kubeadm
requires and the generated default does not include.

## 3 · The private registry — containerd 2.x removed the mirror syntax

Regenerating that config also wiped the registry settings, which looked like this:

```toml
[plugins."io.containerd.grpc.v1.cri".registry.mirrors."192.168.1.201"]
  endpoint = ["http://192.168.1.201:5000"]
```

**Restoring that from backup would not have worked.** containerd 2.x **removed** this
syntax — a config still carrying it is parsed without complaint and silently ignored. So
this had *also* been dead since 27 June; it simply had not been noticed because images
were already pulled.

The 2.x replacement is `certs.d`:

```
/etc/containerd/certs.d/192.168.1.201/hosts.toml
    server = "http://192.168.1.201:5000"
    [host."http://192.168.1.201:5000"]
      capabilities = ["pull", "resolve"]
      skip_verify = true
```

Needed because the manifests reference `192.168.1.201/<image>` with **no port**, so
containerd defaults to HTTPS on :443 against a registry that speaks plain HTTP on :5000.

### RESOLVED — `use_local_image_pull = true`

The symptom: `ctr images pull --hosts-dir /etc/containerd/certs.d` worked perfectly, while
`crictl pull` still tried `https://192.168.1.201:443` — even with `config_path` set on
**both** relevant plugins and `containerd config dump` confirming both were loaded.

**The cause is a containerd 2.x default:**

```toml
[plugins.'io.containerd.cri.v1.images']
  use_local_image_pull = false        # <- the 2.x default
```

With `false`, CRI does not pull images itself — it **delegates to the transfer service**
(`io.containerd.transfer.v1.local`), which keeps its own registry-host configuration.
Setting `config_path` on the CRI images plugin therefore has no effect on CRI pulls, which
is why the setting looked correct and did nothing. Setting it on the transfer service too
was still not enough in 2.2.1.

**The fix** is to make CRI use its own puller, which honours the config it is given:

```toml
use_local_image_pull = true
```

**Verified properly, not by "it looks fine":** an image was deleted from the `k8s.io`
namespace (`ctr -n k8s.io images rm`), confirmed absent (`0`), then pulled with `crictl`
alone — no manual `ctr` step — and confirmed present (`2`). Done on both nodes. A newly
pushed tag that existed on no node also resolved and pulled.

**What this restores:** `docker push` is once again sufficient to deploy. Before the fix,
every deployment required SSHing to each node and running `ctr -n k8s.io images pull`,
because `ctr images pull` without `-n` lands images in the `default` namespace where
kubelet cannot see them.

## 4 · `imagePullPolicy: Always` on `:latest`

Kubernetes defaults `:latest` tags to `imagePullPolicy: Always`, so kubelet insisted on
contacting the registry even with the image sitting locally. Every pod restart therefore
depended on a working registry pull, which turned any transient registry problem into a
visible outage.

**Fixed in the manifests** — 37 files, private-registry images only. Public images (istio,
postgis) keep `Always`, since those come from the internet and benefit from freshness
checks.

## What the images actually are

Pushed from a Mac, they are **OCI image indexes**, not Docker v2 manifests:

```
404  application/vnd.docker.distribution.manifest.v2+json
200  application/vnd.oci.image.index.v1+json
       ├── linux/amd64 manifest        (correct architecture)
       └── attestation manifest        (BuildKit provenance/SBOM)
```

Docker Desktop's BuildKit adds provenance attestations by default, producing an index
rather than a plain manifest. Anything requesting only the old Docker media type gets a
404. Not itself a fault, but it explains why these images are fussier than expected.

**Open question:** Abdul reports pulls failing when Docker Desktop on his Mac is shut
down. No mechanism for that has been established — a registry on `.201` with persistent
storage (16 GB, bind-mounted) should not care. The most likely explanation is indirect:
with `imagePullPolicy: Always`, every pod restart required a successful pull, so any
registry hiccup became an outage that happened to coincide. **Recorded as unexplained
rather than guessed at.**

---

## The lesson worth more than the four fixes

All four were **silent**. Roughly **10,000 combined restart attempts** across two services,
over five weeks, with nothing watching. Two systems were simultaneously broken and serving
traffic, and the only thing that revealed it was an accidental reboot.

Individual bugs are cheap to fix. **The absence of anything that notices is the real
defect.** A check as crude as "any service stuck in `activating`" or "any filesystem above
90 %" would have caught every one of these weeks earlier.
