# Vision-Led Perspective v6: Adaptive Client Priority Narrative System

> Purpose: solve the problem of pitching the same value proposition to every client.
> This version upgrades v5 from a single-priority classifier into a client-priority
> operating system that adapts the report, demo, portal, and proposal to what the
> buyer is actually trying to achieve.

---

## 1. Verdict on the v5 Process

**Score: 8.1 / 10**

The v5 process is directionally correct and much stronger than a default
cost-savings pitch. It correctly recognizes that a prospect chasing a strategic
target, such as reaching 500 organizations in 2026, should not be sold primarily
on monthly savings. It also introduces useful mechanics: priority detection,
confidence tiers, a p0 pre-step, demo routing, portal KPI mapping, and ROI lenses.

However, it is not yet strong enough for live sales strategy because it still
depends too heavily on selecting one dominant priority. Real buying decisions are
usually mixed. A CEO may care about the 2026 growth target, a COO may care about
execution capacity, a CFO may care about budget risk, and the operator may care
about workload. A stronger framework must preserve the primary narrative while
also giving every stakeholder a reason to agree.

### What v5 Gets Right

- It rejects one-size-fits-all cost-savings messaging.
- It forces priority detection before writing the report or demo script.
- It separates direct evidence from weak inference through confidence tiers.
- It changes hero metrics, portal KPIs, demo flow, and proposal ROI by priority.
- It protects against hallucinated vision claims in data-poor accounts.
- It makes cost reduction a valid but non-default lens.

### What v5 Still Misses

- It forces the prospect into exactly one priority too early.
- It treats cost reduction as a fallback, even when a CFO or finance buyer may be decisive.
- It does not fully separate "what the client wants" from "what blocks it" and
  "how the platform proves it."
- It does not create a stakeholder-specific narrative map for CEO, COO, CFO,
  operator, and customer.
- It has a static scoring table, but no evidence quality weighting for recency,
  source reliability, role relevance, or contradiction risk.
- It has discovery validation mainly for Tier C, but even Tier A and Tier B need
  a confirmation loop before final proposal framing.
- It risks over-polishing the pitch before the client's true buying reason is confirmed.

## 2. Stronger Principle

Do not sell the platform.
Do not sell automation.
Do not sell cost savings by default.

Sell the client's next important outcome, then prove that the current operating
model cannot reach that outcome reliably without a better system.

The strongest pitch is:

```text
Your stated or inferred goal is X.
The bottleneck preventing X is Y.
The platform removes Y by doing Z.
The proof is visible in this demo screen.
The business impact is measured in the metric your buyer already cares about.
```

This turns the narrative from:

```text
We can save you money.
```

into:

```text
We can help you achieve the outcome you already care about, with operational proof.
```

## 2A. Self-Audit: Problems in the v6 Concept

The v6 concept is stronger than v5, but it can still fail if the operator treats
it as a heavy template instead of a decision system. These are the problems found
in the v6 process and the fixes added in this improved version.

| Problem | Why It Hurts the Sale | Improvement Added |
|---|---|---|
| Too many priorities can create confusion | A pitch that tries to say everything usually lands nowhere | Limit the client-facing narrative to one Primary Priority, one Secondary Priority, and one Decision Risk |
| Customization may happen too early | Time is wasted building a deep report for a prospect who has not confirmed interest | Add a Fit Gate and Personalization Depth rule before full deliverables |
| Priority detection may become overconfident | Public research can be outdated, aspirational, or incomplete | Treat every priority as a hypothesis until validated by the buyer |
| Contradictory signals are not visible enough | A founder may talk about growth while job posts reveal cost pressure or operational stress | Add a Contradiction Register to the strategy card |
| Stakeholder mapping can become generic | Listing CEO, COO, CFO, operator, and customer is not enough if their concerns are invented | Require evidence or mark each stakeholder lens as assumed |
| Demo proof is not tied tightly enough to claims | A beautiful demo can still fail if it does not prove the specific bottleneck is solved | Add a Claim-to-Screen Proof Map |
| Financial ROI can still weaken the pitch | Weak estimates invite the buyer to argue about math instead of value | Add Metric Integrity rules: sourced, estimated, or excluded |
| No clear next action after validation | The process can produce a strategy but not tell the seller what to do next | Add a Decision Gate with send snapshot, book discovery, build demo, or finalize proposal |
| Manual operations are not translated into buildable platform scope | The pitch may promise transformation without a clear automation blueprint | Add an Automation Opportunity Matrix before report/demo generation |
| Demo claims may exceed real delivery capability | Trust breaks if the prototype implies features that are hard, slow, or expensive to implement | Add Feasibility and Delivery Risk scoring |
| Post-sale handoff is missing | Sales insight can be lost before engineering or implementation starts | Add a Delivery Handoff Brief |
| Future learning is not captured | Every prospect becomes a one-off custom effort | Add a Pattern Library and Outcome Feedback Loop |

### Improved Rule

The framework must produce a **sales decision**, not only a better narrative.

Every prospect must end in one of four next actions:

```text
1. Send 24-hour snapshot only.
2. Book discovery before deeper customization.
3. Build personalized demo and outcome report.
4. Finalize proposal around confirmed buying reason.
```

If the process cannot recommend one of these actions, the process is incomplete.

## 3. The v6 Model: Priority Portfolio, Not Priority Label

Every prospect receives a **Priority Portfolio** instead of only one label.

The portfolio has:

- **Primary Priority:** the lead narrative for the report, demo, and opening pitch.
- **Secondary Priority:** the supporting narrative used to handle other stakeholders.
- **Decision Risk:** the concern that could block the sale if ignored.
- **Proof Asset:** the demo screen or artifact that makes the claim believable.
- **Validation Question:** the question that confirms or corrects the hypothesis.

### Priority Categories

| Priority | Buyer Meaning | Best Lead Narrative | Typical Proof |
|---|---|---|---|
| A. Strategic Growth | "We need to reach a specific growth target." | Capacity to hit the goal faster | Pipeline, onboarding, growth analytics |
| B. Revenue Expansion | "We need more revenue, deals, or monetization." | Faster conversion and deal throughput | Revenue dashboard, CRM, deal flow |
| C. Operational Throughput | "We need work to move faster with less friction." | Same team, better execution speed | Task queue, automation logs, workflow status |
| D. Customer Experience | "We need the customer or partner journey to feel better." | Better service quality and responsiveness | Client portal, self-serve onboarding, status updates |
| E. Risk and Control | "We need visibility, compliance, accountability, or fewer mistakes." | Fewer blind spots and clearer governance | Audit trail, approvals, exception handling |
| F. Cost and Resource Optimization | "We need to reduce waste or avoid unnecessary hiring." | Lower operating cost or avoided headcount | Cost dashboard, effort reduction, break-even model |

Why this is stronger than v5:

- v5 has four priorities.
- v6 has six priorities and recognizes customer experience and risk/control as
  first-class buying reasons.
- v5 chooses one winning bucket.
- v6 builds a portfolio: primary narrative, secondary narrative, and decision risk.

### Portfolio Discipline Rule

The Priority Portfolio is an internal strategy tool. The client should not see
six priorities or a complicated matrix.

Client-facing narrative must be limited to:

```text
Primary Priority: the headline reason to buy.
Secondary Priority: the supporting business case.
Decision Risk: the concern that must be handled so the deal can move.
```

Everything else stays behind the scenes.

## 4. Evidence-Based Priority Scoring

Do not score only the presence of a signal. Score the quality of the evidence.

Each evidence item should be captured like this:

| Field | Required Output |
|---|---|
| Source | Website, LinkedIn, job post, review, call transcript, proposal note |
| Exact Signal | Short quote or paraphrase with citation |
| Priority Supported | A, B, C, D, E, or F |
| Evidence Type | Direct quote, observed behavior, hiring signal, inference |
| Recency | Current, recent, old, unknown |
| Buyer Role | CEO, COO, CFO, operator, customer, unknown |
| Confidence | High, medium, low |
| Contradiction | Any evidence that weakens this interpretation |

### Scoring Formula

Use this simple weighted model:

```text
Evidence Score =
Priority Signal Strength
x Source Reliability
x Recency Weight
x Buyer Role Relevance
x Directness Weight
```

Suggested values:

| Factor | High | Medium | Low |
|---|---:|---:|---:|
| Signal Strength | 5 | 3 | 1 |
| Source Reliability | 1.5 | 1.0 | 0.5 |
| Recency Weight | 1.3 | 1.0 | 0.6 |
| Buyer Role Relevance | 1.4 | 1.0 | 0.7 |
| Directness Weight | 1.5 | 1.0 | 0.6 |

### Classification Rules

- If the top priority beats the second by more than 25%, use a clear Primary Priority.
- If the top two are within 25%, use a Primary + Secondary narrative.
- If the top priority is based only on weak inference, mark it as provisional.
- If the buyer role is unknown, avoid overcommitting the narrative.
- If cost is second or third, keep it as proof, not the headline.
- If cost is first and the CFO/finance buyer is clearly involved, lead with cost.
- If a direct strategic target exists, use it as the North Star only when the
  current operational bottleneck clearly connects to that target.

### Confidence Language Rules

The narrative language must match the evidence quality.

| Evidence Quality | Allowed Language | Forbidden Language |
|---|---|---|
| Direct quote from buyer or official source | "Your stated goal is..." | None, if cited correctly |
| Strong public pattern, no direct quote | "Your current trajectory suggests..." | "You said..." |
| Weak inference | "One possible bottleneck may be..." | Any confident strategic claim |
| Contradictory evidence | "There are two possible priorities to validate..." | Pretending the conflict does not exist |
| No evidence | "We need to confirm this in discovery." | Any invented goal, number, or urgency |

### Contradiction Register

Every p0 strategy file must include a short contradiction register:

```markdown
## Contradiction Register

| Signal A | Signal B | Conflict | How to Handle |
|---|---|---|---|
| Founder talks about scaling to 500 organizations | Job post emphasizes lean operations and budget limits | Growth ambition may be constrained by resources | Lead with growth capacity, keep avoided hiring as CFO support |
```

If there are no contradictions, write:

```text
No material contradictions found in available evidence.
```

## 6. Correct Process for the Client Problem

The correct process is not:

```text
Research prospect -> detect one priority -> generate report -> pitch that priority.
```

The stronger process is:

```text
Research prospect
-> identify strategic goal
-> identify operational bottleneck
-> map manual operations into automation opportunities
-> check feasibility and delivery risk
-> build priority portfolio
-> map stakeholder narratives
-> create proof-led demo
-> validate assumptions
-> finalize report and proposal around confirmed buying reason
```

### Step 0: Run the Fit Gate

Before deep customization, decide whether the prospect deserves full effort.

| Fit Signal | Good Fit | Weak Fit |
|---|---|---|
| Clear business goal | Specific target, expansion, revenue, CX, risk, or efficiency need | Generic website with no visible urgency |
| Visible bottleneck | Manual process, slow workflow, weak follow-up, reporting gaps | No identifiable operational pain |
| Buyer relevance | Founder, executive, operator, or finance role is visible | No clear decision-maker or owner |
| Demo proof | Existing platform can visibly solve the bottleneck | Solution would require inventing unrelated capabilities |
| Timing | Current hiring, campaign, launch, growth push, or public initiative | No sign of near-term change |

Recommended action:

```text
High fit: build personalized demo and outcome report.
Medium fit: send 24-hour snapshot and book discovery.
Low fit: do not build full custom assets yet.
```

### Step 1: Capture the Client's Goal

Find what the client is trying to achieve.

Examples:

- Reach 500 organizations in 2026.
- Expand into a new market.
- Increase sales conversion.
- Reduce onboarding time.
- Improve partner experience.
- Avoid hiring more coordinators.
- Reduce reporting errors.

If the goal is explicit, quote it.
If it is inferred, label it as inferred.
If it is unknown, do not invent it.

### Step 2: Identify the Bottleneck Blocking the Goal

A vision without a bottleneck is a weak pitch.

For every goal, answer:

```text
What operational problem makes this goal harder, slower, riskier, or more expensive?
```

Example:

```text
Goal: reach 500 organizations in 2026.
Bottleneck: partner onboarding and follow-up are too manual to scale reliably.
```

### Step 3: Choose the Primary Priority

Use the strongest evidence to pick the lead narrative.

For the 500 organizations example:

```text
Primary Priority: Strategic Growth
Why: the client has a specific expansion target.
Lead narrative: infrastructure to reach 500 organizations faster and more reliably.
```

### Step 4: Choose the Secondary Priority

Use secondary priority to support the rest of the buying committee.

For the 500 organizations example:

```text
Secondary Priority: Operational Throughput
Why: the growth target depends on coordination capacity.
Supporting narrative: the same team can handle more partner volume without chaos.
```

Cost savings may still appear, but only as supporting evidence:

```text
This may also reduce manual hours and avoid future hiring, but the main value is
not saving money. The main value is making the 500-organization target operationally possible.
```

### Step 5: Build the Demo Around Proof

The demo should not say:

```text
Here are the features.
```

It should say:

```text
Here is the bottleneck preventing the goal.
Here is the screen that removes it.
Here is the metric showing why it matters.
```

### Step 6: Validate Before Final Proposal

Before finalizing the proposal, ask:

1. "Is the 2026 growth target still the right outcome to anchor around?"
2. "Which matters most right now: faster growth, smoother operations, better partner experience, or lower cost?"
3. "Who else will judge this decision, and what will they care about?"

This prevents a beautiful but wrong pitch.

### Step 7: Confirm the Buying Reason

After discovery or the first demo response, update the Strategy Card.

Use this rule:

```text
If the buyer confirms the Primary Priority, keep the narrative and move to proposal.
If the buyer confirms the Secondary Priority instead, rewrite the report hero and proposal lead lens.
If the buyer introduces a new priority, re-run the Priority Portfolio.
If the buyer only asks about price, move cost from support lens to decision-risk lens.
```

### Step 8: Choose the Personalization Depth

Not every prospect should receive the same level of work.

| Evidence + Interest Level | Deliverable |
|---|---|
| Low evidence, no response yet | No full build. Send only a short snapshot or outreach note |
| Medium evidence, no confirmed buyer | 24-hour snapshot plus generic proof screen |
| Strong evidence, buyer engaged | Personalized outcome report and demo |
| Priority confirmed by buyer | Final proposal and pitch script |

This protects the team from spending serious time on unvalidated accounts.

### Step 9: Create the Delivery Handoff

Before moving from sales to implementation, translate the winning pitch into a
buildable scope.

The handoff must answer:

```text
What manual operations did we promise to remove?
Which platform features remove them?
Which demo screens proved the promise?
Which claims are sourced, estimated, or still unvalidated?
What data, access, and integrations are required?
What should not be promised in the first implementation?
```

This prevents the sales narrative from becoming disconnected from delivery.

## 7. Stronger Example for the 500 Organizations Case

### Weak Pitch

```text
This platform saves your team 37 hours per week and $10,000 per month.
```

Why it is weak:

- It assumes money is the main concern.
- It reduces a strategic growth problem into an expense problem.
- It may invite the buyer to challenge the financial math.
- It does not connect directly to the goal they already care about.

### Stronger Pitch

```text
Your 2026 target is not primarily a cost problem. It is an execution-capacity problem.
If the team needs to reach 500 organizations, the question is whether the current
manual operating model can onboard, track, follow up with, and report across that
many relationships without losing momentum.

The platform is valuable because it gives that growth target an operating system:
pipeline visibility, automated follow-up, partner self-service, task routing, and
leadership reporting. Cost savings are a secondary benefit. The primary value is
making the 500-organization target faster, more manageable, and more believable.
```

### Best Demo Opening

```text
I would not frame this demo around saving money first. Your public goal is to
reach 500 organizations in 2026, so the real question is operational capacity:
can every interested organization be captured, followed up, onboarded, supported,
and reported on without the team becoming the bottleneck?

I am going to show you the system that makes that possible.
```

### Best Report Hero

```text
The operating system for reaching 500 organizations in 2026
```

Hero metrics:

| Metric | Better Frame |
|---|---|
| Partner pipeline visibility | Know every organization by stage, owner, and next action |
| Onboarding capacity | Move more partners through the process without proportional headcount |
| Follow-up reliability | Reduce lost opportunities caused by manual tracking |

Cost can appear later:

```text
Secondary benefit: the same system may also reduce manual coordination hours and
avoid future admin hiring. But that is not the headline.
```

### Priority Portfolio for This Case

```text
Primary Priority:
Strategic Growth - reaching 500 organizations in 2026.

Secondary Priority:
Operational Throughput - the team needs enough execution capacity to handle that volume.

Decision Risk:
The buyer may worry whether the financial estimate is accurate or whether the team
can adopt the system quickly.

Proof Asset:
Partner pipeline view + onboarding queue + automated follow-up sequence.

Validation Question:
"Is the 500-organization target still the most important outcome to anchor this around,
or is the current pressure more about team workload, partner experience, or budget?"
```

### Claim-to-Screen Proof Map

| Claim | Screen That Proves It | What To Show |
|---|---|---|
| "You can see every organization by stage" | Partner Pipeline | Stage, owner, next action, stalled accounts |
| "Follow-up no longer depends on memory" | Automation Sequence | Trigger, email status, next scheduled action |
| "Onboarding can scale without chaos" | Onboarding Queue | Pending approvals, completion status, missing items |
| "Leadership can track progress toward 500" | Growth Analytics | Current partners, pipeline trend, capacity against target |

## 8. Deliverable Mapping

### Outcome Report

Lead with the client's desired outcome.

Use this structure:

1. Current goal: what the client is trying to achieve.
2. Current bottleneck: what makes the goal harder today.
3. Operational system: what the platform changes.
4. Proof screens: where the demo shows the change.
5. Business impact: primary metric plus secondary lenses.
6. Decision path: what to validate next.

### Demo

The demo should follow:

```text
Pain -> Proof -> Possibility -> Stakeholder value
```

Do not show the most impressive screen first.
Show the screen that proves the primary bottleneck is solved.

### Proposal

The proposal should contain three ROI layers:

1. **Primary ROI:** aligned with the Priority Portfolio.
2. **Stakeholder ROI:** CEO, COO, CFO, operator, customer.
3. **Financial ROI:** cost, payback, avoided hiring, and implementation effort.

This lets the buyer agree emotionally, operationally, and financially.

### Discovery Validation

Discovery is not a separate sales ritual. It is the correction mechanism for the
Priority Portfolio.

Use this structure:

```text
1. Confirm the goal.
2. Confirm the bottleneck.
3. Confirm the metric that matters.
4. Confirm the buying committee.
5. Confirm the risk that could stop the decision.
```

Then revise the Strategy Card before final proposal.

## 9. Current and Future Problems the Process Must Handle

The improved concept must support the current workflow and also survive future
growth. These are the main risks and the process changes that solve them.

### Current Problems

| Problem | What Can Go Wrong | Process Improvement |
|---|---|---|
| Public data is incomplete | The team may infer the wrong priority or workflow | Mark public-data claims as hypotheses and validate before proposal |
| Manual operations are found but not translated into product scope | The report sounds strategic but does not guide what to build | Use the Automation Opportunity Matrix |
| Demo is too impressive but not operationally honest | Client expects features that are not feasible in v1 | Add Feasibility and Delivery Risk scoring |
| ROI math is weak | Buyer argues against the estimate instead of the transformation | Use a Metric Integrity Ledger |
| Stakeholder concerns are assumed | CFO, COO, or operator objections appear late | Add stakeholder evidence status: sourced, inferred, or unknown |
| Every client gets over-customized | The team burns time on low-fit prospects | Use Fit Gate and Personalization Depth |
| Report and demo drift apart | Report claims one thing, demo proves another | Use Claim-to-Screen Proof Map |
| Sales promise is not handed to delivery | Engineering starts from a vague pitch | Create a Delivery Handoff Brief |
| Adoption risk is ignored | Client buys but team does not use the platform | Add operator workflow and adoption-risk notes |

### Future Problems

| Future Risk | Why It Matters Later | Process Improvement |
|---|---|---|
| Scaling to many prospects | Custom analysis becomes slow and inconsistent | Build a reusable Pattern Library by industry and workflow type |
| Stale research | Public goals, hiring, and priorities change | Add source dates and refresh research before final proposal |
| AI hallucination risk | Generated reports may overstate claims | Require source-to-claim traceability |
| Industry-specific compliance | Healthcare, finance, education, and nonprofit workflows may have trust constraints | Add a Data, Privacy, and Compliance Check |
| Integration complexity | Real automation depends on CRM, email, payment, ERP, or legacy systems | Score integration risk before promising timeline |
| Larger buying committees | More stakeholders means more objections | Keep Primary, Secondary, and Decision Risk lenses in the strategy card |
| Platform maintenance | Bespoke demos can become hard to maintain | Reuse modules and label custom features clearly |
| Pricing pressure | Buyers may compare only cost if strategic value is weak | Keep cost as support unless confirmed as the buying reason |
| Post-sale proof | Client may ask whether the platform actually delivered outcomes | Add an Outcome Feedback Loop after implementation |

### Automation Opportunity Matrix

This is the missing bridge between company analysis and platform design.

Use it immediately after manual operation detection:

```markdown
| # | Manual Operation | Evidence | Role Affected | Current Pain | Automation Feature | Demo Screen | Business Outcome | Priority | Feasibility |
|---|---|---|---|---|---|---|---|---|---|
| 1 | [task done manually] | [source] | [role] | [pain] | [feature] | [screen] | [outcome] | [A-F] | [easy / medium / hard] |
```

Rule:

```text
No report claim or demo pitch can be created unless it traces back to a row in
the Automation Opportunity Matrix.
```

### Metric Integrity Ledger

Every number must be classified before it appears in a report or proposal.

| Metric Type | Label | How To Use |
|---|---|---|
| Directly sourced | [From Source] | Can be used confidently with citation |
| Calculated from sourced inputs | [Calculated] | Show formula briefly |
| Estimated from assumptions | [Estimated] | Use carefully; never make it the only proof |
| Unknown or weak | [Excluded] | Do not use in client-facing material |

Rule:

```text
If the financial estimate is weak, do not lead with money. Lead with capacity,
throughput, experience, risk control, or strategic progress.
```

### Feasibility and Delivery Risk Score

Every automation idea should be scored before being promised.

| Score | Meaning | Sales Rule |
|---|---|---|
| Low Risk | Uses existing platform pattern, simple data, no hard integration | Safe to show and propose |
| Medium Risk | Requires some custom workflow or integration | Show as possible, validate scope before pricing |
| High Risk | Requires unknown data, complex integration, compliance, or heavy custom logic | Do not promise as v1 without technical discovery |

### Pattern Library

To scale the business, every repeated manual operation should become a reusable
pattern.

Examples:

| Pattern | Reusable Module |
|---|---|
| Manual lead tracking | CRM pipeline + owner assignment |
| Manual follow-up | Email/SMS automation sequence |
| Manual onboarding | Self-serve onboarding flow |
| Manual reporting | Dashboard + scheduled report export |
| Manual approvals | Approval queue + audit trail |
| Manual billing explanation | Calculator + billing dashboard |

This helps the company avoid rebuilding a different custom system for every prospect.

### Outcome Feedback Loop

After implementation, capture whether the promised outcome happened.

```text
Promised outcome -> implemented feature -> measured result -> client feedback
-> reusable proof point -> improved future pitch
```

This turns delivery results into stronger future sales evidence.

## 10. Improved End-to-End Workflow

The process should now be:

```text
1. Company Research
2. Manual Operation Detection
3. Automation Opportunity Matrix
4. Feasibility and Delivery Risk Score
5. Fit Gate
6. Evidence Table + Contradiction Register
7. Priority Portfolio
8. Narrative Strategy Card
9. Claim-to-Screen Proof Map
10. 24-Hour Snapshot or Discovery
11. Outcome Report
12. Demo Pitch
13. Proposal
14. Delivery Handoff Brief
15. Outcome Feedback Loop
```

This is the best alignment with the business model because it keeps automation at
the center and uses narrative only to explain why the automation matters.

## 11. Quality Guardrails

Use these rules before sending any client-facing narrative:

- Do not lead with cost unless finance pressure is the confirmed buying reason.
- Do not use a strategic goal unless it is sourced or clearly labeled as inferred.
- Do not use estimated financial math as the main proof if the calculation is weak.
- Do not pitch automation as the value. Pitch the outcome automation makes possible.
- Do not treat the decision-maker as the only audience.
- Do not bury the client's own goal under generic platform features.
- Do not generate the final proposal before validating the priority hypothesis.
- Do not claim the platform guarantees the goal; claim it removes bottlenecks that
  make the goal easier, faster, or more controllable.
- Do not show more than one primary story in the client-facing report.
- Do not build full custom assets until the Fit Gate justifies the effort.
- Do not hide contradictory evidence. Resolve it or validate it in discovery.
- Do not include a metric unless it is sourced, estimated with a clear basis, or
  intentionally excluded.
- Do not create a report claim unless it maps to a manual operation and automation feature.
- Do not show a demo screen unless it supports a real business claim.
- Do not promise high-risk automations without technical discovery.
- Do not let a sales narrative move forward without a delivery handoff.

## 12. Final Evaluation Framework

Use this checklist to score any report, demo, or proposal:

| Question | Pass Standard |
|---|---|
| Does the narrative name the client's actual goal? | Goal is quoted or carefully inferred |
| Does it identify the bottleneck blocking the goal? | Bottleneck is operational and specific |
| Does the demo prove the bottleneck is removed? | Screen route maps to pain points |
| Does the report lead with the right metric? | Metric matches the Primary Priority |
| Does it support other stakeholders? | Secondary and risk lenses are present |
| Are cost savings used correctly? | Lead only when confirmed; otherwise support |
| Are assumptions labeled? | Estimates and inferences are marked |
| Is there a validation loop? | Discovery questions are included before final proposal |
| Is there a Fit Gate decision? | Deliverable depth matches evidence and buyer interest |
| Are contradictions handled? | Conflicts are listed and resolved or queued for discovery |
| Is every major claim proven by a screen? | Claim-to-screen map exists |
| Is there one clear next action? | Snapshot, discovery, demo/report, or proposal |
| Does every claim map to an automation opportunity? | Automation Opportunity Matrix row exists |
| Has feasibility been checked? | Delivery risk is low, medium, or high |
| Is there a handoff to implementation? | Must-build, should-build, and do-not-promise are documented |
| Can the learning be reused? | Pattern Library or feedback loop is updated |

Scoring:

```text
9-10: Client-specific, proof-led, stakeholder-aware, validated, and action-ready.
7-8: Strong narrative, but missing a gate, contradiction handling, or proof map.
5-6: Personalized on the surface but still template-driven.
Below 5: Generic pitch with swapped company names.
```

## 13. Recommended Replacement for v5

Use v5 as the foundation, but replace its single-priority operating model with
this v6 process:

```text
Phase 1: Research
Phase 1A: Manual Operation Detection
Phase 1B: Automation Opportunity Matrix
Phase 1C: Feasibility and Delivery Risk Score
Phase 0A: Fit Gate
Phase 0B: Evidence Table + Contradiction Register
Phase 0C: Priority Portfolio
Phase 0D: Narrative Strategy Card + Claim-to-Screen Proof Map
Phase 2: 24-hour snapshot or discovery, if priority is not validated
Phase 3: Outcome Report using Strategy Card
Phase 4: Demo and Portal using Claim-to-Screen Proof Map
Phase 5A: Discovery Validation
Phase 5B: Final Proposal using confirmed buying reason
Phase 6: Delivery Handoff Brief
Phase 7: Outcome Feedback Loop and Pattern Library update
```

This is stronger because it solves the real problem:

```text
Every client has a different reason to buy.
Every stakeholder has a different reason to approve.
Every claim needs proof.
Every priority hypothesis needs validation.
```

The new process does not merely customize the pitch. It customizes the reason the
client should believe the pitch.
