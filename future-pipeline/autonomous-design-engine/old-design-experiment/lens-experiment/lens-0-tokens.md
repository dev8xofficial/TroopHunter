## Primary Input Sources

Read these reconstruction files to perform the analysis:

1. `{{token_dir}}/global/*.tokens.ts` — all primitive token files (color, typography, spacing, radius, shadow, etc.)
2. `{{token_dir}}/semantic/semantic.tokens.ts` — semantic token mappings
3. `{{globals_css}}` — CSS variable definitions
4. `{{tailwind_config}}` — Tailwind token mapping
5. `{{feature_ui}}` — screen-specific feature components (for usage context)
6. `{{shared_ui}}` — shared UI components (for usage context)

**Lens 0 file priority:** Token definition files (`token_dir`, `globals_css`,
`tailwind_config`) are your primary sources. Feature and shared component
files provide usage context — read them to understand where and how tokens
are applied, but extract values from the token system itself.

## Reconstruction Code Reading Protocol

When reading the reconstruction codebase:

1. Read all token files first to build the complete token vocabulary.
2. Read component files to see how tokens are applied in practice.
3. For each extracted value, mark it as:
   - CONSISTENT — used across multiple components or screens
   - VARIANT — used differently in different contexts (note each variant)
   - ISOLATED — appears in only one component or context
4. In the final output, only CONSISTENT values become hard tokens.
   VARIANT values become token ranges. ISOLATED values are noted but
   marked as non-canonical.

## Confidence Scale

Tag every extracted value with a confidence level:
  HIGH   — value explicitly defined in token files or directly readable from Tailwind classes
  MEDIUM — value inferred from component composition or conditional logic
  LOW    — value implied by layout structure but not directly expressed in code

Do NOT omit LOW confidence values — flag them so Phase 8 knows
which constraints to enforce loosely.

## Step 2 — Token Extraction

Extract values for each category. For every value, provide:
  - The value itself (hex, px, CSS string — be precise)

  - Confidence level (HIGH / MEDIUM / LOW)

### Colors
List every distinct color defined in the token system. Group by visual
role — but let the roles emerge from the token structure, not from a
preset list. Common roles include primary, accent, background, surface,
border, text — but name new roles if the design has colors that don't
fit these.

For each color:
  [hex] — role: [name] — used for: [specific elements] — [confidence]

If a gradient is used, provide the full CSS-ready definition:
  [linear-gradient(angle, stop1 pos%, stop2 pos%, ...)] — [context] — [confidence]

### Typography
List every distinct text size and weight combination defined in the
token system and used in components. Do NOT limit yourself to 3 levels.
Find all of them.

For each typography level:
  Size: [px] — Weight: [number] — Color: [hex] — Context: [where used] — [confidence]

Note: If a text element uses BOTH large size AND thin weight (or small
size AND heavy weight), flag this explicitly as it affects hierarchy logic.

### Spacing
List the spacing values defined in the token system. Work at three levels:
  Level A — Page / Section gaps: [values in px]
  Level B — Component-to-component gaps (grid gutters): [values in px]
  Level C — Intra-component padding: [values in px]

Note: Level B (inter-component) is NOT the same as Level A (inter-section).
A grid may use 4px gutters between cards even when sections are 32px apart.
Capture both independently.

## Step 3 — Decorative Patterns

This section captures sub-token visual identity markers — patterns that
cannot be described as a single color, size, or radius value, but are
major contributors to the design's feel and recognizability.

Read component files and look for:
- Repeated line patterns (dotted, dashed, hatched, striped) in Tailwind classes or CSS
- Texture overlays (grain, noise, canvas, mesh)
- Geometric pattern fills
- Decorative inner elements (rings, glows, halos, inner borders)
- Overlapping or layered element techniques (stacking, z-depth)
- Gradient mesh or multi-color background transitions
- Anything that is NOT a component but contributes to the visual surface

For each pattern found:
  Pattern: [name or description]
  Location: [where it appears in the codebase]
  CSS representation: [the actual CSS/Tailwind used]
  Visual role: [what it adds to the design — texture / depth / separation / identity]
  [confidence]

If no decorative patterns are found in the code, state that explicitly.
Do NOT invent patterns that don't exist.

## Step 4 — Anti-Tokens

List visual treatments this design clearly does NOT use, based on what
is absent from the token system and component implementations. This is
as important as what it does use — these become the Prohibited section
of the Design Specification.

Consider:
  - Is there any hard drop shadow defined? (yes / no)
  - Are there any sharp border-radius values (0–8px) on interactive elements?
  - Is any high-contrast color used as a pure decoration (no semantic role)?
  - Are there any aggressive weight contrasts (e.g., 100 weight next to 900)?
  - Is there any full-saturation color that dominates the composition?
  - Are any elements underlined, outlined, or bordered with strong contrast?

Format:
  This design does NOT use: [description]
