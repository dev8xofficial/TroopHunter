I've been building using AI code assistants for over a year now. For 30 years I have been a professional software engineer, with deep experience in well over a dozen languages. I've built my own database server, my own programming language, my own operating system. I've done a lot - long before AI became available. 

And now with AI? Not much has changed - it's still solely dependent on how strong of an engineer is controlling the AI. Like all things software: Garbage in, Garbage out. 

During the course of the year I have spent with AI, I have tried to "vibe code" a couple of apps. The experience was not great. It generated something that will work for 1 use case. But in my experience it's not possible to ship a production ready product using this technique. My results: it won't scale. It's littered with bugs, security holes, and duplicated features. And lots and lots of extra, unnecessary code. Order O(2*n)^2 performance. Debugging it takes, longer with multiple attempts/PR's before the bug is solved. 

But if I approach it with proper practices, providing it details, plans, guiding it with correct technique, demanding it meets certain quality gates before moving onwards - it works. I can fix bugs in one shot. I understand the whole of the system, every detail of every function, class, module, library, etc. It also doesn't over-engineer anything - I can get it to create what I want in a minimal amount of code, knowing that true elegance comes from a solution that can run in as few lines of code as possible. Less LoC, less to maintain, less to read, less to know. The best engineers I know spend a lot of time avoiding writing code, and yet have the best outcomes.

In my experience, you can't truly vibe code a real production ready app. You can create a prototype, you can create a PoC, you can build a fantasy. But to make that reality requires real true engineering. So it comes back down to what it has always been - the quality of the app comes from the quality of the engineering, and an AI assistant can't fix that. Building your craft can. AI assistants are just another tool in the engineer's tool box - and we need to use them appropriately.

I’ve been using Claude Code with Opus 4.8 workflows, GPT-5.5 in Codex, and OpenClaw on the side as my personal assistant.

My honest take:

The next big developer skill is not prompting.

It’s agent management.

The models writing code is old news. What feels different now is the handoff.

With Opus 4.8 workflows, I can give it a scoped task, let it explore the repo, form a plan, split work across subagents, edit files, run tests, and come back with something I can actually review.

It still gets things wrong. Sometimes confidently. Sometimes in ways that only show up when you run the actual app.

But that’s the point. The value is not “trust it blindly.”

The value is: give it bounded work, make it produce evidence, then review the result like you would review a junior engineer’s PR.

Codex with GPT-5.5 feels useful in a slightly different way. I like it for debugging, repo-aware edits, review passes, and messy tasks where the agent needs to move through files, commands, tests, and diffs without losing context.

OpenClaw fills another gap entirely. It’s not my coding agent as much as my continuity layer: project context, research, client updates, loose threads, and the stuff around the code that still matters.

That combination feels like the real shift.

Not “AI writes code now.”

More like: AI can help operate parts of the development process, if you give it the right constraints.

And that “if” is doing a lot of work.

Can you define the task clearly?
Can you keep scope tight?
Can you avoid handing the agent access it does not need?
Can you tell the difference between code that compiles and software that actually works?
Can you review the diff, run the tests, check the UI, and catch the weird edge cases?

That’s where the leverage is.

Used badly, these tools are a bug accelerator.

Used well, they let a small team punch way above its weight.

I don’t think AI removes the need for engineering judgment.

I think it makes weak engineering judgment more expensive and strong engineering judgment more valuable.

I kept running into the same problem with AI coding agents.


They would help with a change, miss a real issue, I would correct it, and then a few days later they would make the same kind of mistake again.


Not weird edge cases. Normal things that break apps:


- auth checked in the UI but not on the server

- tenant boundaries that looked right until you followed the query

- webhook handlers that were fine until the provider retried

- tests that passed because the risky part was mocked away

- review comments that treated preferences like blockers


So I started writing down the context I wanted the agent to have before it reviewed or changed code.


I cleaned it up and put it here:

https://lnkd.in/gT8eEjtz


The most useful part is probably code-review-guide.md. It's written for the agent, not really for a person. The goal is to push reviews toward concrete risk: file/line evidence, severity, impact, and a fix direction.


It's not official docs. It's not meant to be impressive. It's just the kind of practical reference I wish I had sooner for Next.js, Supabase, TypeScript, Stripe, webhooks, Vitest, and Playwright work.


I'd like this to become more than my own notes, though. If other devs have better patterns, repeated AI failure cases, corrections, or examples from their own stack, I'd love to collaborate and make it as strong as possible.
